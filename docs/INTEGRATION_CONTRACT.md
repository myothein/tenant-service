# Tenant-service API contract (draft, not production)

This service is provisioned for **one fixed tenant** via TENANT_ID. The request may not select a tenant using x-tenant-id or x-tenant-code headers. Each tenant must have an isolated database/role and correct schema.

**Auth:** /subjects now requires an RS256-signed JWT from TENANT_OIDC_ISSUER and TENANT_OIDC_JWKS_URL (same HTTPS origin outside loopback). The token must have a valid signature, audience TENANT_OIDC_AUDIENCE, expiry, issued-at, subject, tenant_id equal to fixed deployment TENANT_ID, and TENANT_OIDC_REQUIRED_ROLE (default TENANT_ADMIN). Keycloak `realm_access.roles` and top-level `roles` are supported only after cryptographic verification. /local-events retains a **separate temporary agent Bearer API key**; mTLS/rotation are release blockers. Shared admin API key requires explicit TENANT_ADMIN_AUTH_MODE=legacy, TENANT_ALLOW_DEV_API_KEY=true, and is **forbidden** with NODE_ENV=production. Never run production in legacy mode.

**Endpoints:** GET /health public liveness; /subjects (list/create/update/delete) tenant-scoped; GET /local-events/pending and PATCH /local-events/:id/mark-sent agent-only. GET /students and GET /students/:id provide a *read-only* tenant-scoped directory using the audited db-helper `student` table (`tenant_code`, `"deletedAt"`, `"classId"`, `"gradeId"`), with strict pagination, opaque-ID validation and a minimal projection of `id`, `name`, `surname`, `classId`, `gradeId`. Other-tenant and soft-deleted rows are not returned. Read responses exclude contact information, birthday, medical data, address and photos. **Student mutations are DEFAULT-DENY**: POST /students, PUT /students/:id (name/surname only), DELETE /students/:id (soft delete) require a tenant-admin authenticated request and explicit TENANT_STUDENT_WRITES_ENABLED=true. In production the request must carry a verified OIDC subject; QA-only legacy authentication never works in production. Create validates fixed tenant and class/grade ownership, mandatory schema fields and whitelist inputs. Mutations use one PostgreSQL transaction for the domain row and pending local_events outbox event; failure must roll back both. Event payload contains only student ID, tenant code and class/grade IDs; OIDC subject goes in event headers for audit attribution. Neither event nor mutation response contains address, email, birthday, medical data or phone. Full student enrollment, bulk imports, privileged role review and downstream processing remain NOT production-accepted. GET /users is a read-only, verified-tenant-admin directory using the isolated tenant DB and an explicit field projection (id, username, first_name, last_name, is_active, role_id, created_at, updated_at), sorted by username/id, with page/limit (1–100, offset <= 1,000,000). It never returns email or SELECT *; missing/invalid authorization is rejected before database access; tenant selection headers are rejected. POST/PUT/PATCH/DELETE /users are denied with HTTP 405. No user provisioning or role mutation is exposed.

**Outbox contract:** subject and opt-in student mutations persist the domain row and local_events insert in one SQL transaction; event ids are UUID strings and must be preserved by the agent. Agent may acknowledge local event only after persisting it in its own durable SQLite outbox; retries must not create duplicate IDs. Central ingestion, delivery receipts, authentication and safe backup/recovery remain release blockers.

**DB contract:** db-helper tenant Prisma schema owns subject and local_events table definitions. There is NO automatic migration on service startup. Apply migrations explicitly to isolated DEV only after a verified backup and review.

**Unresolved:** Real Keycloak role/scoped write authorization, student data privacy approval, production audit retention, user role authorization, production identity (OIDC/mTLS), automatic encrypted credential rotation, tenant-agent token injection, PostgreSQL integration tests, end-to-end central event ingestion, Windows service acceptance. Production NO-GO.


## Durable student-write idempotency (Draft / not a production approval)

For opt-in `POST /students`, `PUT /students/:id`, and `DELETE /students/:id`, clients **must** send one fresh `Idempotency-Key` per logical mutation, generated with a cryptographically secure random source (for example UUIDv4). The server rejects a missing key with HTTP **428**, malformed or repeated headers with **400**, and reuse of an existing key for a different operation, resource, normalized request, or authorized principal with **409**. An accepted retry replays the original HTTP 201/200 response with `Idempotency-Replayed: true` without a second domain write or outbox record. A retry after a domain/outbox transaction rollback may execute normally because the ledger reservation rolls back too.

The `student_write_idempotency` table is an additive, **not automatically applied** db-helper migration, version `20261123151000_student_write_idempotency`. A unique `(tenant_code,key_digest)` key serializes concurrent retries across processes; the reservation, student write, outbox insert and stored response commit in one transaction. Raw idempotency tokens and raw request data are not persisted. The request fingerprint is a SHA-256 HMAC keyed by the client-generated random token; stored response JSON is limited to opaque student ID and class/grade references, with no name, contact, birthday or health details.

**Migration order:** db-helper initial tenant schema → local_events → student_write_idempotency. Apply only in approved isolated DEV/QA after backup verification; production migrations and runtime DB grants need separate owner review. Keep the ledger immutable for replay correctness until a documented retention/purge and backup policy is approved. The stored pseudonymous student identifier still requires access controls. Do not enable student writes when the migration, audited OIDC tenant-admin mapping, least-privilege grants and disaster recovery gates are not complete.
